You are a senior Python/ML engineer. Build a clean, modular MVP for a hackathon project called **Pair Research Agent**.

The goal is to create the complete local foundation before we get access to Langfuse, Distil Labs, Autoresearch, and Runpod.

The project is NOT a live trading bot and must NOT execute real trades. It is a quantitative research and backtesting system that identifies potentially interesting stock pairs for a market-neutral long/short pair-trading strategy.

The most important architectural requirement is:

**The LLM/agent decides what to investigate. Deterministic Python tools perform all mathematical and statistical calculations.**

Later, we want to:
1. send agent traces to Langfuse,
2. turn successful and failed traces into evaluation/training data,
3. train a smaller model with Distil Labs / Autoresearch,
4. deploy that model on Runpod,
5. send its interactions back into Langfuse.

Design the codebase so these integrations can be added later without rewriting the core system.

---

# 1. Main workflow

The system should support a request such as:

> "Find a suitable pair for NVDA."

or:

> "Find the 5 most promising pair-trading candidates among these stocks."

The workflow should be:

User request
→ Agent receives available stocks
→ Agent identifies reasonable candidate peers
→ Agent calls deterministic research tools
→ correlation screening
→ cointegration test
→ spread construction
→ stationarity test
→ half-life estimation
→ backtest
→ out-of-sample evaluation
→ agent selects or rejects a pair
→ structured research report
→ full trace saved locally
→ evaluator assigns objective scores

The agent MUST be able to conclude:

> "No sufficiently robust pair was found."

It must never be forced to select a pair.

# 6. Quantitative tools

Implement every statistical calculation as a deterministic Python tool.

The LLM must NEVER manually calculate these metrics.

## Correlation

Calculate return correlation rather than only price-level correlation.

Return:

```python
{
    "correlation": 0.87,
    "n_observations": 500
}
```

---

## Cointegration

Use an Engle-Granger cointegration test using `statsmodels`.

Return at minimum:

```python
{
    "test_statistic": ...,
    "p_value": ...,
    "passes_threshold": true
}
```

Threshold must be configurable, default e.g. `0.05`.

---

## Spread

Estimate a hedge ratio using OLS.

Do NOT simply assume a 1:1 ratio.

Represent spread approximately as:

```text
spread = stock_A - beta * stock_B
```

Return beta and the resulting spread.

Prevent accidental use of future information.

---

## Stationarity

Run an Augmented Dickey-Fuller test on the spread.

Return:

```python
{
    "adf_statistic": ...,
    "p_value": ...,
    "stationary": true
}
```

---

## Half-life

Estimate the mean-reversion half-life of the spread.

Handle invalid/non-mean-reverting cases gracefully.

Return `None` or a structured failure rather than producing meaningless values.

---

# 7. Time-series discipline

This is critically important.

Prevent:

- look-ahead bias
- data leakage
- random train/test splitting of time-series data

Use chronological splits.

Make the split configurable, but support something conceptually similar to:

```text
Research/train period:
2022-01-01 → 2024-12-31

Validation:
2025-01-01 → 2025-12-31

Held-out test:
2026-01-01 → latest available date
```

If current market data does not contain all these periods, adapt intelligently while preserving chronological ordering.

All parameters such as:

- hedge ratio
- spread mean
- spread standard deviation
- entry threshold

must be estimated using the training/research period only and then applied to later periods where appropriate.

# 8. Pair-trading backtest

Implement a simple, transparent pair-trading backtest.

Use the spread z-score.

Initial default rules:

```text
z-score > +2:
short spread

z-score < -2:
long spread

|z-score| < 0.5:
close position
```

Make thresholds configurable.

Include:

- hedge ratio
- transaction costs
- position changes
- no future information
- market-neutral or approximately beta-neutral construction where practical

Do NOT optimize parameters on the held-out test set.

Return metrics including:

```python
{
    "total_return": ...,
    "annualized_return": ...,
    "annualized_volatility": ...,
    "sharpe_ratio": ...,
    "max_drawdown": ...,
    "number_of_trades": ...,
    "win_rate": ...
}
```

Calculate train and validation/test metrics separately.

A pretty equity curve is useful but secondary to correctness.

# 11. Pair scoring

Create a transparent pair-quality score from 0–1 or 0–100.

Do NOT use in-sample Sharpe alone.

Use several components such as:

- statistical validity
- cointegration
- spread stationarity
- sensible half-life
- out-of-sample performance
- train → validation degradation
- drawdown
- transaction-cost robustness

For example conceptually:

```text
25% statistical validity
25% out-of-sample performance
20% temporal stability
15% drawdown
10% transaction-cost robustness
5% efficiency
```

Do not blindly copy these weights if a better formulation is obvious.

Keep each component available separately so we can later use them as Langfuse evaluation scores.

# 12. Agent abstraction

Create a common agent interface.

Example:

```python
class ResearchAgent(ABC):
    def research(self, request: ResearchRequest) -> AgentResult:
        ...
```

Implement two agents.

## A. HeuristicResearchAgent

This MUST work without any LLM API.

It should:

1. parse a requested ticker/universe
2. get peer candidates
3. screen correlations
4. run deeper analysis on promising candidates
5. rank them
6. reject weak candidates
7. return the best pair(s)

This gives us a deterministic baseline.

## B. LLMResearchAgent

Create an OpenAI-compatible abstraction.

The LLM should decide:

- which candidates are worth investigating
- which tools to call next
- when enough evidence exists
- whether a pair should be rejected
- which final pair is best

But the LLM must use deterministic tools for every numerical/statistical claim.

Do not tightly couple the implementation to one provider.

Use environment variables for:

```text
LLM_BASE_URL
LLM_API_KEY
LLM_MODEL
```

This is important because later `LLM_BASE_URL` may point to Runpod.

If no API key is configured, the project must still work using `HeuristicResearchAgent`.

# 22. Correctness priorities

Correctness matters more than sophisticated UI.

In particular:

1. NEVER use future observations when generating historical signals.
2. NEVER randomly split time series.
3. NEVER calculate statistical values inside the LLM.
4. NEVER treat high correlation alone as evidence of a valid pair.
5. NEVER force the agent to choose a pair.
6. NEVER optimize against the held-out test set.
7. Explicitly account for transaction costs.
8. Gracefully handle insufficient or bad market data.
